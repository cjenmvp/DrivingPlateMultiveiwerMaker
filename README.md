# 드라이빙플레이트 멀티뷰어 v3.1.1

영상 최대 9개를 3×3, 1920×1080 멀티뷰 영상으로 합성합니다. 기존 자동 배치, 슬롯별 LUT, 오버레이, 대기열을 유지하면서 파일명과 입력 코덱에 대한 의존성을 줄였습니다.

## 실행

이 Mac에서는 `dist/DrivingPlateMultiviewer_v3_1_1.app`을 더블클릭하세요. FFmpeg와 FFprobe가 포함됩니다. 기존 v1/v2 앱은 변경하지 않습니다.

소스 실행:

```sh
.venv/bin/python main.py
```

다른 환경에서는 Python 3.9 이상과 `requirements.txt`의 패키지, FFmpeg/FFprobe가 필요합니다. FFmpeg 빌드에는 `drawtext`, `xstack`, `lut3d`, `libx264`, `libx265`, `prores_ks`가 있어야 합니다. 설치된 실행 파일과 기존 static-ffmpeg 설치본을 탐색하며 자동으로 다운로드하지 않습니다. `FFMPEG_BINARY`, `FFPROBE_BINARY` 환경변수로 실행 파일을 지정할 수도 있습니다.

## 폴더를 드래그해서 자동 배치

앱 상단의 파란 점선 영역에 폴더를 놓으세요. 한 폴더는 화면에 즉시 배치되고, 여러 폴더는 첫 폴더를 보여주면서 모두 대기열에 추가합니다. 대기열 영역에 놓으면 폴더 하나도 대기열로 추가합니다. 폴더 드롭은 선택된 수동/순서 모드와 관계없이 번호 자동 배치를 사용합니다.

```text
10_  | 12_       | 02_
09_  | Top_/13_  | 03_
08_  | 06_       | 04_
```

`02_서울.mov`, `03_부산.mp4`처럼 선두 카메라 번호를 우선합니다. `03_서울_02_take.mov`는 03번 카메라입니다. `uuid-1234_02_서울.mov`처럼 접두어 뒤의 독립된 번호도 인식합니다. `102_`를 `02_`로 인식하지 않으며, 미사용 선두 번호 `01_` 뒤의 테이크 번호도 카메라로 사용하지 않습니다. 한 슬롯에 후보가 여러 개면 빈칸으로 남기고 로그에 알립니다. 하위 폴더는 재귀 탐색하지 않습니다.

## 파일명 없이 사용하는 방법

1. **영상 직접 추가…**로 여러 파일을 선택합니다. 빈 슬롯 순서대로 배치됩니다. 폴더를 먼저 스캔할 필요가 없습니다.
2. 원하는 슬롯을 클릭하거나 파일을 해당 슬롯에 드래그하면 위치를 직접 지정할 수 있습니다. **비우기**는 해당 칸만, **전체 비우기**는 전체 배치를 지웁니다.
3. 저장 위치와 출력 코덱을 선택합니다. 저장 위치에 폴더를 드롭하면 전체 경로가 입력됩니다. 비우면 작업의 원본 폴더에 저장하고, 상대 경로를 입력하면 원본 폴더 아래의 경로로 처리합니다. 해당 폴더가 읽기 전용이거나 쓰기 권한이 없으면 다른 저장 폴더를 선택하는 창이 나타납니다. 선택을 취소하면 원본과 대기열을 유지합니다.
4. **프리뷰 생성**으로 최대 1초를 확인한 다음 **렌더링 시작**을 누릅니다.

폴더 배치 방식은 세 가지입니다. 변경한 뒤 **현재 폴더 다시 배치**를 누르세요.

- **기존 네이밍으로 자동 배치**: `10 / 12 / 02`, `09 / Top 또는 13 / 03`, `08 / 06 / 04`. 중복 후보는 임의로 고르지 않고 로그에 표시합니다.
- **파일명 순서로 9칸 배치**: 네이밍 규칙과 관계없이 파일명 정렬 순서로 배치합니다. 9개 초과분은 로그로 알립니다.
- **수동 배치**: 빈 슬롯으로 시작하여 직접 지정합니다.

자동 배치 결과는 항상 화면에서 확인하세요. 대기열에 폴더를 드래그하면 번호 자동 배치를 사용합니다. 수동 배치는 화면에서 구성한 후 **대기열 추가**를 사용하세요.

## 코덱과 합성

- 입력: ProRes MOV, H.264, HEVC 등 **선택한 FFmpeg가 디코딩할 수 있는 영상**. MOV/MP4/MXF/MKV/AVI/MTS/M2TS/WebM 등을 폴더에서 찾습니다. 직접 선택의 **모든 파일**은 확장자 제한 없이 영상 스트림을 검사합니다.
- 출력: H.264 MP4, H.265 MP4, ProRes 422 MOV, ProRes 422 HQ MOV.
- ProRes 출력은 10비트 4:2:2입니다. H.264/H.265 출력은 8비트 4:2:0입니다. 자동 모드는 Apple VideoToolbox 하드웨어 인코딩을 우선 사용합니다. CPU 모드도 선택할 수 있습니다.
- 서로 다른 해상도와 프레임레이트는 슬롯당 640×360, 첫 번째 사용 슬롯의 FPS로 통일합니다. 비율은 유지하고 여백은 검정 처리합니다.
- 길이는 기본적으로 가장 짧은 영상에 맞춥니다. 가장 긴 영상에 맞추면 먼저 끝난 슬롯은 마지막 프레임을 유지합니다. 모두 각 영상의 시작 시각부터 재생하며 타임코드 기반 동기화는 하지 않습니다.
- 빈 칸은 검정, 출력에는 오디오가 없습니다. Log/HDR 원본을 자동으로 Rec.709 변환하지 않으므로 필요한 LUT를 지정하세요. ProRes RAW는 지원을 보장하지 않습니다.
- 기존 출력은 덮어쓰지 않고 `_v2`, `_v3`를 붙입니다. 임시 폴더에 렌더링한 뒤 성공한 파일만 저장하며, 취소/실패 시 임시 파일은 정리됩니다.
- 대기열에는 추가 시점의 출력 코덱·길이·가속 설정이 저장됩니다. LUT 설정 변경은 기존 동작대로 대기 중인 작업에도 적용됩니다.

## Mac 가속과 성능

기본값 **자동 · Apple 하드웨어 우선**을 사용하세요. 실제 하드웨어 인코더 생성이 가능한지 검사한 후 H.264/HEVC/ProRes에 VideoToolbox를 사용합니다. 하드웨어를 사용할 수 없으면 CPU로 진행하며, 자동 모드의 하드웨어 렌더링이 실패하면 CPU로 한 번 재시도합니다. 실제 선택된 인코더 이름과 재시도 여부가 로그에 표시됩니다.

이는 Apple 전용 미디어 엔진을 이용한 **인코딩 가속**입니다. 입력 디코딩·리사이즈·LUT·3×3 합성은 CPU에서 처리하므로 GPU 사용률이 높지 않아도 정상입니다. FFmpeg의 [VideoToolbox 구현](https://www.ffmpeg.org/doxygen/7.0/videotoolboxenc_8c.html)을 사용합니다.

CPU 작업도 코어 수에 맞게 조정합니다. LUT는 640×360으로 축소한 다음 적용하므로 큰 원본에서 연산량이 줄어듭니다. 이 순서는 v3.0의 원본 크기 LUT 적용과 경계 픽셀의 색이 조금 다를 수 있습니다.

Apple M3 Ultra 실측 — 1080p30 ProRes/H.264 입력을 번갈아 9슬롯에 배치, 3초 합성 샘플, LUT 없음, 각 2회 중앙값:

| 출력 | v3.0 CPU | v3.1 CPU | v3.1 하드웨어 | v3.0 대비 |
| --- | ---: | ---: | ---: | ---: |
| H.264 | 2.00초 | 1.07초 | 0.86초 | 약 2.33배 |
| HEVC | 2.33초 | 1.39초 | 0.88초 | 약 2.66배 |
| ProRes 422 | 3.49초 | 1.36초 | 1.32초 | 약 2.65배 |

합성 샘플의 결과이며 장시간 4K/8K 원본·스토리지·LUT 사용에 따라 차이가 있습니다. CPU는 CRF, 하드웨어 H.264/HEVC는 각각 15/10Mbps를 사용하므로 동일 화질 조건의 코덱 효율 비교는 아닙니다. [원시 측정값](benchmarks/m3-ultra-v3.1.json)과 `scripts/benchmark.py`로 재현할 수 있습니다.

## 검증 및 빌드

```sh
QT_QPA_PLATFORM=offscreen .venv/bin/python -m unittest discover -s tests -v
.venv/bin/pyinstaller --noconfirm DrivingPlateMultiviewer_v3_1.spec
```

테스트는 실제 ProRes/H.264 혼합 입력, 4종 출력 코덱, 다른 FPS·영상 길이, 빈 슬롯과 배치 위치의 픽셀, 특수문자 파일명·오버레이·LUT, 중복 네이밍 및 스캔 없는 수동 배치를 검사합니다. 현재 앱 빌드는 Apple Silicon Mac용이며 Windows 실행 검증은 하지 않았습니다.

실제 하드웨어 검증과 이전 버전 비교:

```sh
MULTIVIEW_TEST_HARDWARE=1 .venv/bin/python -m unittest discover -s tests -v
.venv/bin/python scripts/benchmark.py --reference-ref 9f93be7 --report /tmp/benchmark.json
```

앱 버전은 `version.py`, 변경 내역은 `CHANGELOG.md`에서 관리합니다. GitHub Actions는 push/PR마다 CPU 렌더링과 폴더 드롭·재시도 테스트를 실행합니다.
